## 1. 문서 개요

### 1.1 배경

초기 PRD는 `PMO본부 업무수행 현황_260331.xlsx`와 `2026년 PMO본부 KPI_가동율_260410.xlsx` 두 엑셀 파일을 브라우저에서 재현하는 MVP를 목표로 작성되었다.

현재 프로젝트는 해당 방향을 유지하되, 프로젝트 운영·인력 관리·공휴일·데이터 백업/복원까지 구현 범위가 확장되었다.

1. P1: 프로젝트 운영 원장, 프로젝트 코드, 프로젝트 상세, 진행이력, 홈 대시보드
2. P2: 인력 마스터 및 영업대표 연동 구현, 인력 투입/배정 원장 개편 진행
3. P3: 공휴일·백업/복원·기능 권한 모델·통제된 전체 초기화 구현, 권한 UI·실제 원본 전환 후속
4. P4 이후: KPI 집계, 보고 화면, 다운로드 산출물 정교화

### 1.2 이번 PRD의 핵심 변경

이번 문서는 이상적인 최종 설계가 아니라, **현재 구현된 프로젝트를 기준으로 최신 요구사항을 재정렬한 기준 문서**다.

핵심 변경은 다음과 같다.

1. P1 프로젝트 운영 기능은 프로젝트 코드와 프로젝트의 1:1 정합성을 포함해 구현되어 있다.
2. 홈, 업무수행현황, 프로젝트 관리, 프로젝트 상세, 진행이력은 실제 API와 연결되어 있다.
3. 인력 관리는 실제 API와 연결되었고 PMO본부 인력/영업대표 후보를 관리한다. 인력 투입 현황과 주간/월별 보고는 아직 mock 또는 정적 화면 성격이 강하다.
4. 인력 유형은 PMO본부·영업대표·기술본부·기타/외부의 4종으로 확장하고 `personnel_type`을 SSOT로 도입한다.
5. `대기/제안 현황`, `제안PRJ`, `이행PRJ`, `대기/제안인원`, `보고서 다운로드`의 별도 메뉴는 구현하지 않고 운영 화면 필터, 주간현황 상세 테이블, 화면별 다운로드 중심으로 정리한다.
6. 로컬 계정 로그인은 아직 실제 구현되지 않았고, 백엔드는 개발용 헤더 기반 사용자 주입으로 권한 흐름을 검증 중이다.
7. 데이터 백업/복원 페이지는 통합 JSON 백업·복원을 제공한다. 프로젝트·인력 엑셀은 각 관리 페이지로 분리했고, 2026-10-13 기존 통합 엑셀 검증·전체 교체 UI/API를 제거했다. 기존 업로드 이력은 조회 전용으로 유지한다.
8. 프로젝트별 투입 인력은 평상시 프로젝트 상세에서 수동 관리하며, 최초 원본 전환 시에만 별도 투입 파일을 1회성으로 업로드한다.
9. PMO본부 가동률·가득률의 분모는 무조건 PMO본부 인력만 포함한다.

### 1.3 제품 비전

PMO본부의 프로젝트 운영 원장, 인력 투입 원장, 기준일 스냅샷, KPI 집계, 보고 다운로드를 하나의 내부 시스템으로 통합한다.

최종적으로 사용자는 다음 업무를 브라우저에서 수행할 수 있어야 한다.

- 프로젝트 등록/조회/수정
- 프로젝트 코드 및 마스터 관리
- 프로젝트 상세 일정/금액/PM/진행이력 관리
- 인력 재직/역할/배정 관리
- PMO본부·영업대표·기술본부·기타/외부 인력 구분 관리
- 기준일 현재 투입 현황 확인
- 상태 KPI 카드 필터를 통한 수행/제안/지원/대기 인력 목록 확인
- 월별 MM, 가동률, 가득률 집계 확인
- 보고용 엑셀 다운로드
- 프로젝트·인력 마스터의 권한 기반 엑셀 다운로드/업로드
- 업무 데이터 전체 백업/복원과 통제된 초기화

## 3. 목표와 범위

### 3.1 제품 목표

1. 기존 엑셀 2종의 핵심 운영 흐름을 브라우저에서 재현한다.
2. 프로젝트 운영 원장과 프로젝트 코드를 DB 기준으로 구조화한다.
3. 진행이력을 별도 데이터로 저장하고 프로젝트 상세 및 전체 이력 화면에서 조회한다.
4. 인력 재직/배정/현재 투입 스냅샷을 DB 기준으로 관리한다.
5. 월별 MM, 주간 KPI, 월별 KPI를 백엔드 집계 결과로 제공한다.
6. 보고용 엑셀 다운로드를 화면별로 제공한다.
7. 프로젝트와 인력 마스터를 각 관리 페이지의 별도 엑셀로 관리한다.
8. 프로젝트별 투입 인력은 별도 원장으로 관리하고 프로젝트 상세에서 수동 등록·수정한다.
9. 프로젝트·인력·배정·이력·MM·스냅샷·KPI를 하나의 데이터 세트로 백업·복원한다.
10. 고위험 작업은 역할 레벨과 별도의 기능 권한으로 통제한다.

### 3.2 현재 MVP 우선순위

현재 MVP 우선순위는 다음 순서로 둔다.

| 우선순위 | 범위 | 상태 |
|---|---|---|
| P1 | 프로젝트 운영 원장/코드/상세/진행이력 | 핵심 구현 완료, 엑셀 업로드 후속 |
| P2 | 인력 마스터/영업대표/배정 원장 | 인력·영업대표/4종 유형·전체 보기·전용 엑셀, 프로젝트 상세 배정 원장/수동 등록·수정·종료·취소 구현. 인력 투입 메인/숨김 상세 연계 후속 |
| P3 | 공휴일/데이터 백업·복원/관리자 기능 | 공휴일·백업/복원·권한 모델·초기화 구현, 권한 UI·실제 적용 후속 |
| P4 | KPI 집계/주간·월별 보고 | 일부 모델 존재, 구현 필요 |
| P5 | 화면별 다운로드/마스터 업로드 | 프로젝트·인력 다운로드 구현, 분리 업로드 후속 |

### 4.1 주요 사용자

- 팀장
- PM
- PL
- 조회 전용 사용자
- 관리자

### 4.2 권한 코드

현재 백엔드 enum 기준 권한은 다음과 같다.

| 권한 | 코드 | 설명 |
|---|---|---|
| 조회 전용 | `read_only` | 조회만 가능 |
| 일반 수정 가능 사용자 | `general_editor` | 프로젝트 및 마스터 수정 가능 |
| 프로젝트 담당 수정 가능 사용자 | `project_editor` | 담당 프로젝트 조건부 수정 |
| 관리자 | `admin` | 전체 수정 가능 |

### 4.3 현재 인증 구현 상태

MVP 원칙은 로컬 계정 방식이지만, 현재 구현은 아직 실제 로그인/JWT가 아니다.

현재 API는 개발용 요청 헤더로 사용자를 주입한다.

- `x-user-name`
- `x-user-email`
- `x-user-permission`

기존 일반 CRUD는 헤더가 없으면 기본 관리자 사용자로 처리한다. 기능 권한 API는 별도 개발용 이메일 어댑터로 DB 사용자를 조회하며 헤더의 기본 권한/개발자 여부를 신뢰하지 않는다. 누락·미등록 사용자는 401, 기능 권한 부족은 403이다. production 모드에서는 해당 개발용 어댑터를 차단한다.

### 4.4 권한 정책

현재 구현된 정책은 다음과 같다.

1. `read_only`는 프로젝트/프로젝트 코드/진행이력 등록과 수정을 할 수 없다.
2. `admin`, `general_editor`는 프로젝트 등록/수정이 가능하다.
3. `project_editor`는 프로젝트가 발표완료 이후 상태이고, 본인이 해당 프로젝트 PM인 경우 수정할 수 있다.
4. 프로젝트 코드 마스터 수정은 현재 `admin`, `general_editor`만 가능하다.
5. 본부장 마스터 수정 허용 여부는 후속 정책 확정이 필요하다.

최종 권한 정책은 기존 권한 레벨과 별도로 기능 권한을 사용한다.

| 기능 권한 | 허용 범위 |
|---|---|
| `project_excel_manage` | 프로젝트 엑셀 다운로드·검증·업로드 |
| `personnel_excel_manage` | 인력 엑셀 다운로드·검증·업로드 |
| `assignment_manage` | 프로젝트별 투입 인력 등록·수정 및 승인된 1회성 업로드 |
| `backup_restore` | 통합 JSON 백업 생성·조회·삭제·복원 |
| `data_reset` | 업무 데이터 전체 초기화 |
| `permissions_manage` | 관리자 임명 및 사용자별 기능 권한 부여 |

초기에는 개발자 계정만 전체 기능 권한을 가진다. 개발자가 관리자를 임명한 뒤 관리자가 팀장·팀원에게 필요한 기능 권한만 부여한다. 기능 권한은 프론트 버튼 노출과 백엔드 API에서 모두 검증한다.

### 4.5 후속 구현 요구사항

- 로컬 계정 로그인 화면과 세션/JWT 구현
- 사용자 관리 화면 구현
- 조직/팀/본인 프로젝트 범위별 데이터 스코프 적용
- 본부장/팀장 권한 정책 확정
- 수정 이력 감사 로그 추가
- 사용자별 기능 권한 UI 구현 (저장·부여·회수 API는 3번 묶음 반영)
- 개발자/시스템 관리자와 일반 관리자 경계의 UI·운영 인증 연계 (백엔드 경계는 3번 묶음 반영)

현재 구현 정책은 다음과 같다.

- 신규 등록 시 `done` 선택 불가
- `memo`와 `in_progress` 사이 직접 전환 불가
- `done`은 `in_progress`에서만 전환 가능
- `done` 상태 이력은 현재 수정 불가

### 5.7 인력 유형

인력 유형은 소속 본부명이나 역할명을 매번 조합해 추정하지 않고 `personnel_type`으로 관리한다.

| 라벨 | 코드 | PMO 재직/MM/KPI 포함 |
|---|---|---|
| PMO본부 인력 | `pmo` | 포함 |
| 영업대표 | `sales` | 제외 |
| 기술본부 인력 | `technical` | 제외 |
| 기타/회사 외부 인력 | `external` | 제외 |

영업대표는 추가로 `Role.code = SALES_OWNER`를 만족해야 프로젝트 영업대표 후보가 된다. 기존 `group_name = PMO본부`와 역할 기반 판정은 기존 데이터 migration과 유형이 없는 구형 등록·엑셀·백업·seed의 입력 전환에서만 사용한다. 저장 이후 PMO 집계는 명시 유형으로 판단한다. 구형 수정 요청의 유형 누락은 저장된 값을 유지한다.

- 프로젝트 관리 엑셀 검증/업로드

프로젝트 등록 시 현재 API 필수값은 다음과 같다.

- 프로젝트명
- 고객사
- 사업유형
- 상태
- 확도
- 총 사업금액
- 당사 사업금액
- 영업대표
- 영업부서
- 제안PM
- 발표PM
- 수행PM
- 시작일
- 종료일
- 제안 제출일

프로젝트 엑셀 정책은 다음과 같다.

- 다운로드 파일과 업로드 템플릿은 프로젝트 목록의 업무 컬럼을 동일하게 사용한다.

- 제안/수행팀, 최근 활동일, MM, KPI, 스냅샷 등 파생값은 업로드에서 받지 않는다.
- 프로젝트 코드를 식별 기준으로 신규·수정·동일·오류·파일 누락 기존 행을 미리보기한다.
- 파일에 없는 기존 프로젝트는 기본 `유지`이며, 사용자가 `삭제(비활성화)`를 개별 또는 일괄 적용할 수 있다.
- 일반 업로드에서 프로젝트를 물리 삭제하지 않는다.

최종 운영 요구사항:

- 페이지 명칭을 `데이터 백업/복원`으로 변경한다.

- 백업/복원 대상은 프로젝트 코드·프로젝트·인력·배정·진행이력·월별 재직 MM·월별 배정 MM·현재/주간 스냅샷·월별 KPI다.
- 사용자·권한·역할·공휴일·작업 잠금·백업 파일/이력 자체·초기화 감사 이력은 대상에서 제외한다.
- 페이지 하단에 `업무 데이터 전체 초기화` 위험 작업을 제공한다.
- 초기화는 실행 전 자동 백업, 대상별 건수, 확인 문구 직접 입력, `JobLock`, 단일 DB 트랜잭션, 실패 롤백, 감사 이력을 적용한다.
- 운영 환경의 초기화 기능 플래그는 기본 비활성화한다.
- 백업/복원은 `backup_restore`, 초기화는 추가로 `data_reset` 권한이 필요하다.

2026-10-13 전체 초기화 구현: 페이지 하단의 위험 작업에서 10개 업무 테이블 건수 확인 → 확인 문구 `업무 데이터 전체 초기화` 입력 → 자동 JSON 백업/검증 → 초기화 순서로 실행한다. `DATA_RESET_ENABLED=false`가 모든 환경의 기본값이며 저장된 개발자/admin과 두 기능 권한을 재검증한다. 10분 확인 토큰은 사용자와 DB 상태에 묶이고 공통 작업 잠금 및 DB 쓰기 잠금을 적용한다. 삭제와 성공 감사 기록은 동일 트랜잭션이며 실패 시 전체 롤백한다. 별도 `data_reset_audits`는 JSON 복원/초기화 범위 밖에 보존한다. 신규 migration `261013_0023` 적용 및 초기화/복원은 실제 DB 사본에서만 검증했다. 실제 개발 DB는 `261013_0022` 그대로이며 초기화하지 않았다. [9번 구현·검증 기록](harness/data_reset_rollout_261013.md) 참조.

## 8. 계산 정책

### 8.1 가동률/가득률

가동률/가득률은 기존 엑셀 철학을 유지한다.

주간현황은 사람 수 기준이다.

- 가동률 = `(PMO본부 수행 인원 + PMO본부 제안 인원 + PMO본부 지원 인원) / PMO본부 현재 인원`
- 가득률 = `PMO본부 수행 인원 / PMO본부 현재 인원`

월별가동현황은 MM 기준이다.

- 가동률 = `(PMO본부 수행 MM + PMO본부 제안 MM + PMO본부 지원 MM) / PMO본부 재직 MM`
- 가득률 = `PMO본부 수행 MM / PMO본부 재직 MM`

분모와 분자는 모두 `personnel_type = pmo`인 인력만 집계한다. `전체 인력` 화면의 인원 수 또는 비PMO 인력의 배정 MM을 PMO본부 KPI 계산에 재사용하지 않는다.

### 8.2 월별 MM

월별 MM은 사람 × 프로젝트 × 월 기준으로 계산한다.

계산 원칙은 다음과 같다.

1. 월 근무 가능일을 산정한다.
2. 배정 기간과 해당 월의 겹치는 근무일을 산정한다.
3. 주말과 공휴일을 제외한다.
4. `배정 근무일 / 월 근무 가능일`을 기준으로 MM을 산정한다.
5. 확도 반영 MM이 필요한 경우 `certainty_rate`를 별도 weighted 값으로 저장한다.
6. PMO본부 KPI용 월별 재직 MM과 배정 MM은 `personnel_type = pmo`인 인력만 생성·집계한다.

### 8.3 연차 제외

연차 제외 기능은 기존 엑셀에 없으므로 MVP에서 제외한다.

추후 확장 시 연차/휴가 테이블을 추가하고, 월별 MM 계산에서 제외 기간으로 반영한다.

### 8.4 투입률 입력

MVP에서는 배정별 투입률 `%` 입력을 기본 필수값으로 도입하지 않는다.

현재 입력 중심은 다음이다.

- 인력
- 프로젝트
- 배정 유형
- 역할
- 시작일
- 종료일
- 상태
- MM 또는 월별 MM

| 재직/MM 정보 | PMO 계산에 필요한 범위 필수 | 선택 또는 미입력 |
| 역할 | PM/PL 등 | 영업대표만 `SALES_OWNER` 필수 |

### 9.4 프로젝트 배정

프로젝트 배정은 사람 × 프로젝트 × 기간의 원장이다.

필수 관리 항목은 다음과 같다.

- 프로젝트
- 인력
- 배정 유형
- 배정 역할
- 배정 상태
- WIN/LOSS 관련 구분
- 근무 위치 구분
- 대표 배정 여부
- 표시 순서
- 시작일
- 종료일
- MM
- 월별 MM
- 총 MM
- 현재 MM
- 확도
- 비고

P2 기준으로 `WorkLocationType` enum을 추가해야 한다.

- `onsite`
- `remote`
- `hybrid`

배정 원장은 프로젝트·인력 마스터와 별도 생명주기를 갖는다. 일반 운영에서는 프로젝트 상세 화면에서 등록·수정·취소하며 물리 삭제보다 상태 보존을 우선한다.

### 9.5 진행이력

진행이력은 프로젝트에 종속된다.

필수 관리 항목은 다음과 같다.

- 프로젝트
- 이력 상태
- 이전 프로젝트 상태
- 다음 프로젝트 상태
- 기록일시
- 작성자
- 수정자
- 내용

### 9.6 스냅샷과 KPI

스냅샷과 KPI 테이블은 입력 원장이 아니라 계산/마감 결과 성격이다.

필수 데이터는 다음과 같다.

- 기준일 현재 투입 스냅샷
- 주간 투입 스냅샷
- 월별 재직 MM
- 월별 배정 MM
- 월별 KPI 요약

### 9.7 사용자 기능 권한

사용자의 기본 권한 레벨과 별도로 여러 기능 권한을 부여·회수할 수 있어야 한다. 저장 방식은 사용자-기능 권한 매핑 테이블 또는 동등한 정규화 구조로 구현하며, 기능 코드의 SSOT는 백엔드 enum/상수로 관리한다.

사용자·권한 데이터는 업무 데이터 백업/복원 및 전체 초기화 대상에서 제외한다.

## 11. 엑셀 다운로드/업로드 요구사항

### 11.1 현재 구현

현재 프로젝트 화면 계열에는 브라우저 기반 엑셀 다운로드가 일부 구현되어 있다.

- 업무수행현황 다운로드
- 프로젝트 관리 다운로드
- 인력 관리 다운로드

다운로드 파일명은 화면명과 현재 시각을 포함한다.

### 11.2 최신 요구사항

다운로드 정책은 다음과 같이 정리한다.

1. 우선 각 화면에서 현재 필터 결과를 다운로드한다.
2. `제안PRJ`, `이행PRJ`는 별도 페이지보다 업무수행현황 필터 + 다운로드로 대체한다.
3. 통합 `보고서 다운로드` 메뉴는 MVP 필수에서 제외하고 후속으로 둔다.
4. 서버 기준 산출물이 필요한 경우 report export API를 별도 구현한다.
5. 프로젝트와 인력은 각각 해당 관리 페이지에서 별도 엑셀 파일로 다운로드·업로드한다.
6. 다운로드 파일과 업로드 템플릿은 화면 표시용 `-`, 축약 ID, 파생 표시값을 제외한 동일 업무 컬럼 체계를 사용한다.
7. 프로젝트·인력 업로드는 전체 데이터 삭제가 아니라 식별자 기준 추가·수정·선택적 비활성화로 처리한다.
8. 파일에 없는 기존 행은 팝업에서 내용을 보여주고 기본 `유지`, 선택 `삭제(비활성화)`를 제공하며 일괄 적용을 지원한다.
9. 검증한 동일 파일만 반영할 수 있도록 파일 해시/검증 토큰을 사용하고 반영 전 DB 변경 여부를 재검증한다.
10. 프로젝트별 투입 인력은 프로젝트·인력 파일에 포함하지 않는다.

### 11.3 최초 원본 데이터 전환

현재 더미 데이터를 실제 원본 데이터로 전환할 때는 다음 순서를 따른다.

1. 현재 더미 데이터 전체 백업
2. 통제된 업무 데이터 전체 초기화
3. 원본 엑셀에서 인력 업로드 파일 생성
4. 사용자가 빈 인력 정보를 검토·보완한 후 인력 업로드
5. 서버 발급 `personnel_id`가 포함된 인력 파일 재다운로드
6. 프로젝트 업로드 파일 생성·검토·업로드
7. 프로젝트 코드와 `personnel_id`를 기준으로 별도 투입 파일 생성
8. 투입 파일 1회성 검증·업로드
9. 월별 MM·현재/주간 스냅샷·KPI 서버 재생성
10. 프로젝트·인력·배정 건수 대사와 표본 상세 검증

## 12. 비기능 요구사항

### 12.1 사용성

- 화면은 기존 엑셀 사용자가 이해하기 쉬운 컬럼명과 흐름을 유지한다.
- 프로젝트 운영자는 목록에서 상세로 빠르게 진입할 수 있어야 한다.
- 본부장/팀장은 홈, 주간현황, 월별가동현황에서 핵심 KPI를 빠르게 확인할 수 있어야 한다.
- 관리자 화면은 입력 밀도가 높아도 필터/정렬/페이징이 안정적으로 동작해야 한다.

### 12.2 성능

- 목록 API는 페이징을 기본 지원한다.
- 대량 데이터 다운로드는 후속 서버 API로 분리할 수 있어야 한다.
- KPI 화면은 프론트에서 대량 계산하지 않고 백엔드 집계 또는 스냅샷 결과를 사용한다.

### 12.3 데이터 품질

- 프로젝트 코드 중복은 차단한다.
- 프로젝트 등록 필수값 누락은 API에서 차단한다.
- 허용되지 않는 상태 전환은 API에서 차단한다.
- 상태 변경은 자동 진행이력으로 남긴다.
- 배정 취소는 삭제가 아니라 상태 변경으로 보존한다.
- 프로젝트 코드와 프로젝트 마스터는 항상 1:1로 생성·수정되며 코드만 단독으로 남지 않게 한다.
- 프로젝트·인력 업로드는 반영 전에 신규·수정·동일·오류·누락 기존 데이터를 구분해 보여준다.
- PMO본부 KPI는 PMO본부 인력만 분자·분모에 포함한다.
- 백업/복원/초기화 후 프로젝트·인력·배정·MM·스냅샷의 고아 참조가 없어야 한다.

### 12.4 보안

- MVP는 내부망/로컬 계정 기반을 전제로 한다.
- 개발용 헤더 인증은 운영 배포 전에 제거해야 한다.
- 운영 전 로그인, 세션, 권한 검증, CSRF/CORS 정책을 확정해야 한다.
- 프로젝트/인력 엑셀, 백업 파일에는 개인정보가 포함될 수 있으므로 Git 저장 금지, 접근 권한 제한, 다운로드 감사 이력, 보관 기간 정책을 적용한다.
- 엑셀 권한과 백업/복원/초기화 권한은 프론트 노출 제어와 백엔드 인가를 동시에 적용한다.
- 업무 데이터 전체 초기화는 운영 환경에서 기본 비활성화하고 명시적 기능 플래그와 `data_reset` 권한을 모두 요구한다.

- mock 기반 인력 화면 제거 또는 명확한 개발 표시

### 14.3 데이터 운영 릴리스 기준

- 통합 JSON 백업/복원 정상 동작
- 백업 삭제 시 연결된 작업 이력과 파일 정리
- 프로젝트·인력 전용 엑셀과 JSON 백업/복원이 동작하고 제거된 통합 업로드 API를 호출해도 데이터를 변경할 수 없음
- 전체 초기화 전 자동 백업과 확인 문구 적용
- JobLock·트랜잭션·실패 롤백·감사 이력 적용
- 사용자·권한·역할·공휴일·백업 파일은 초기화 대상에서 제외
- 기능 권한의 UI/API 양쪽 검증
- 복원·초기화 후 고아 참조 없음

### 14.4 KPI 릴리스 기준

KPI 범위는 다음 조건을 만족해야 한다.

- 공휴일 데이터 관리
- 월별 재직 MM 계산
- 월별 배정 MM 계산
- 월별 KPI 요약 생성
- 주간 KPI 파생 응답 제공
- 주간현황/월별가동현황 화면 API 연동
- 엑셀 산식과 샘플 데이터 검산
- PMO본부 가동률·가득률의 분자·분모에 PMO본부 인력만 포함됨을 검증

## 15. 최종 정리

현재 프로젝트는 **프로젝트 운영, 인력/영업대표 관리와 유형 선택, 공휴일 관리, 데이터 백업/복원, 프로젝트·인력 전용 엑셀과 프로젝트 상세 투입 배정 원장까지 실제 API와 화면으로 구현한 상태**다. 기능 권한 모델·공통 인가·최소 관리 API는 구현했다. 인력 투입 메인/숨김 상세, KPI/보고 화면, 로그인/기능 권한 UI는 후속 구현 대상이다.

새 기준선은 다음과 같다.

1. P1 프로젝트 운영 기능은 현재 구현을 기준으로 유지/보완한다.
2. `personnel_type`을 도입해 PMO본부·영업대표·기술본부·기타/외부 인력을 명시적으로 관리한다.
3. PMO본부 가동률·가득률과 MM/KPI에는 PMO본부 인력만 포함한다.
4. 프로젝트와 인력은 각 관리 페이지의 별도 엑셀로 다운로드·검증·업로드한다.
5. 프로젝트별 투입 인력은 프로젝트 상세에서 수동 관리하고 최초 원본 전환 때만 별도 파일로 1회성 업로드한다.
6. 데이터 백업/복원은 연결 데이터 전체를 보존하고, 통제된 전체 초기화의 안전장치 역할을 한다.
7. 기존 통합 엑셀 전체 교체는 2026-10-13 UI/API에서 제거 완료했다. 과거 작업 이력과 JSON 백업/복원은 보존한다.
8. 권한은 개발용 헤더 검증에서 로컬 계정 로그인과 기능 권한 기반으로 전환한다.
9. 대기/제안 현황/제안PRJ/이행PRJ/대기·제안인원/보고서 다운로드 별도 메뉴는 구현하지 않고, 운영 화면 필터, 주간현황 상세 테이블, 화면별 다운로드 중심으로 재정리한다.
