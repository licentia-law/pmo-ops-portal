# 최초 원본 투입 배정 전환 도구 구현·검증 기록

2026-10-13, DTL P3.2 0절·22.1의 7번 범위. **도구 구현/검증 완료, 실제 개발 DB 전환 미실행**. 기존 사용자 변경분·업무 DB·3000/8001 서버는 보존했다. 신규 운영 패키지와 DB 스키마 변경은 없다. 실제 원본 엑셀 변환/삭제/초기화는 수행하지 않았다.

## 1. 진단·변경 파일

- 기존 프로젝트/인력 엑셀의 원시 파일 업로드·검증 토큰·백업·공통 잠금, 수동 배정 검증/MM 계산, PMO 스코프·KPI 계산, 인력 스냅샷 갱신을 확인하고 재사용했다. 전체 교체 `_generate_derived_rows`는 기존 이력 덮어쓰기/중복 생성 위험이 있어 호출하지 않았다.
- 새 서비스 `apps/api/app/services/assignment_import.py`, 라우트 `apps/api/app/api/routes/assignment_import.py`, 테스트 `apps/api/tests/test_assignment_import.py`.
- 기존 `app/services/project_assignments.py`에 내부 최초 전환 옵션만 추가. `app/core/config.py` 전환 스위치, `app/main.py` 라우터 등록, `.env.example` 기본 false. 실제 `.env`는 이번 작업에서 변경하지 않았다.
- WEB: `design/pages/AssignmentImportPage.tsx`, `app/(protected)/admin/assignment-import/page.tsx`, `app/lib/api.ts`, `design/pages/DataBackupRestorePage.tsx`, 공통 `packages/shared-types/src/routes.ts`. 사이드바 상시 메뉴는 추가하지 않았고 백업 화면에 권한 있는 사용자용 링크만 추가했다.
- 문서: 현재 PRD, P3.2 DTL, api_guide, policy_implementation_status, schema_project 및 이 기록. `_old`나 deprecated 설계 안내를 구현 기준으로 사용하지 않았다.

## 2. 사용·파일/API 계약

1. 별도 전환 환경에서 `ASSIGNMENT_IMPORT_ENABLED=true` 설정 후 API 실행. development/test만 허용하고 production은 차단한다. 기본값은 false이며 스위치만으로 권한이 생기지 않는다.
2. `/admin/assignment-import` 또는 백업 화면의 `최초 원본 전환용 투입 배정 도구` 링크. 직접 URL/API도 저장된 `assignment_manage`로 인가한다.
3. 전환 양식과 인력 UUID·프로젝트 코드·입력 안내를 다운로드한다. 참조 다운로드의 다중 시트 파일은 업로드하지 않는다.
4. `최초투입전환` 단일 시트 .xlsx, 최대 20MB/5000행. 헤더를 그대로 사용한다. 필수 배정키(200자 텍스트), 프로젝트 코드, personnel_id(UUID), 배정 유형/상태, 시작/종료일, 월 기준 MM. 역할·확도율·상주·대표·순서·비고는 선택이다.
5. 월 기준 MM은 0~9999.99 소수 둘째 자리, 확도율 0~100 소수 둘째 자리(공란 100%), 대표 참/거짓 또는 1/0(공란 거짓), 순서 0~100000 정수(공란 0), 비고 4000자 이내. 코드/한글 라벨을 지원하며 날짜·역할 호환성·참조·활성 상태는 수동 배정 검증을 재사용한다. 총/누적/당월 MM으로 월 기준을 자동 추정하지 않는다.
6. 검증은 읽기 전용이다. 수식·헤더 불일치·빈 필수값·없는 참조·파일 내부 배정키/완전 중복·기존 완전 중복은 오류다. 다른 배정/같은 파일의 기간 겹침, 대표 겹침, 과거 전환, PMO 재직 MM 기간 밖 배정은 경고로 원본 대사를 요구한다. PMO의 필요한 MM 시작일이 없으면 오류로 보완을 요구한다.
7. 오류가 없으면 주의사항·1회 반영을 확인하고 `백업 후 1회 반영`. 사용자/검증 토큰/파일 해시/30분 TTL/전체 업무·휴일 fingerprint를 확인한다. 검증 후 데이터가 바뀌면 재검증한다. 파일 변경 시 UI 검증 결과를 버린다.

API: GET `/api/assignment-import/status`, `/template`, `/references`; POST `/validate`는 x-upload-filename과 원시 xlsx 바이트, POST `/apply`는 `{validation_id,file_sha256,acknowledge_warnings:true}`. 누락 데이터 처리·기존 행 수정·분할 후 추가 반영 옵션은 없다.

## 3. 반영·파생 데이터·복구

- 공통 백업/복원/업로드 작업 잠금, SQLite BEGIN IMMEDIATE 또는 행 잠금, 저장 직전 권한·완료 기록·DB 상태 재확인, 전체 JSON 사전 백업 후 단일 DB 트랜잭션으로 추가한다. 사전 백업 실패/행 반영 실패는 전체 롤백하며 완료 기록을 남기지 않는다. 실패 검증 토큰은 재시도할 수 있다.
- 기존 프로젝트·인력 UUID/FK·배정/로그를 보존하고 신규 assignment UUID를 생성한다. 프로젝트별 메모에 원본 배정키/assignment UUID/파일 해시/값을 남긴다. project_id=NULL 시스템 이력 `[assignment_import_complete]`에 완료 파일/해시/작업자/시각/사전 백업/건수를 남긴다.
- 한 데이터에 성공한 파일 1개만 허용한다. 서버 재시작·캐시 소실·다른 파일도 추가 반영 불가다. 일반 진행이력 CRUD는 프로젝트 없는 시스템 기록을 수정할 수 없다. 완료 후 JSON 백업/복원은 차단 상태를 보존한다.
- 신규 배정의 시작월부터 과거/현재/미래 월별 MM을 생성한다. 취소·미투입은 0, 확도율 0%도 그대로 0이다. 현재 비활성/퇴직 인력이라도 과거 종료 배정 이력은 보존·계산한다. 과거/취소 상태 신규 허용은 전환 서비스 내부에서만 사용하며 수동 등록 정책은 유지한다.
- 기존 재직 MM을 덮어쓰지 않고 PMO 유형의 MM 기준 기간에 없는 월만 보완한다. PMO 인력만 오늘 현재/주간 스냅샷에 포함하고 오늘의 기존 스냅샷 UUID/비고는 공통 helper 기준으로 유지한다. 과거 스냅샷은 변경하지 않는다.
- 기존 과거 KPI는 보존하고 없는 과거 월만 생성한다. 현재/미래 KPI는 PMO 범위 공통 helper로 갱신한다. 기존 조회가 원장 기반 PMO projection을 제공하는 점은 유지된다. 비PMO도 프로젝트 배정/월별 MM에 보존되며 PMO 분자/분모에는 포함되지 않는다. 산식 정의는 변경하지 않는다.
- 재전환이 필요하면 자동 생성된 **전환 전 백업 ID**로 백업/복원 화면에서 복원하고 원본/건수를 다시 확인한다. 이 복원은 당시 업무 데이터 전체로 돌아가므로 이후 입력 데이터도 포함해 복구 계획을 검토해야 한다. 실제 DB 복원은 이번 작업에서 실행하지 않았다. 자동 JSON 백업의 사용자·권한·역할·공휴일 제외 정책은 유지된다.
- 반영 성공 후 manifest 저장 실패는 DB 성공을 실패로 보고하지 않고 경고한다. 완료 SSOT는 DB 기록이며 백업 파일은 유지된다.

## 4. 검증 결과

- 백엔드 최종 전체 회귀 **154 passed, 1 skipped**. 건너뜀은 구버전 0019 개발 사본 대상 테스트이며 신규 임시 DB/대표 기존 스키마 upgrade·downgrade·FK 검증은 통과했다. 이후 인력 재직 시작월이 첫 배정보다 이전인 경우의 누락 MM 생성 테스트를 추가한 전환 범위 **26 passed**, 최종 Ruff·전체 타입 검사·변경 프론트 범위 린트도 통과했다. 기존 utcnow deprecation 등 경고는 실패로 숨기지 않고 유지했다.
- TestClient가 현재 환경에서 종료됨을 확인했다. Windows 소켓 제한 밖에서 임시 SQLite DB와 세션 override로 실행했으며 실제 DB를 테스트 fixture로 쓰지 않았다.
- 임시 DB의 4종 인력 전환, MM/가중 MM, 비PMO KPI 제외, UUID/FK·과거 원장 보존, 권한/production/스위치 차단, 참조/필수/정밀도/날짜/수식 오류, 기존/파일 중복·겹침 경고, 토큰 사용자/해시/만료/DB 변경, 재반영 차단, 두 번째 행 실패의 전체 롤백·잠금 해제·재시도, 사전 백업 실패, 완료 후 JSON round-trip 및 전환 전 복구를 검증했다.

## 5. 실제 적용 여부·남은 작업

- **실제 개발 DB 적용 없음**: 스키마 변경도 없어 migration head `261013_0022` 유지. 전환 플래그 기본 false/실제 .env 미변경. 실제 원본 파일 반영/더미 삭제/초기화는 미실행.
- 실제 전환 전에 월 기준 MM의 원본 의미, 인력 UUID/프로젝트 코드, PMO MM 시작/종료일과 배정 기간, 해당 연도 공휴일 기준을 검토해야 한다. 재직 기간 밖 배정 경고가 있으면 원본 대사를 마친 뒤 판단해야 하며 산식이나 기간을 자동 조정하지 않는다.
- 대용량 원본의 속도 검증/운영 로그인 연결은 실제 도입 준비에서 추가 확인한다. 5000행 초과는 현재 한 번만 허용되는 단일 파일 계약 때문에 임의로 분할 반영하지 않는다.
- 다음은 22.1 **8번 통합 엑셀 업로드 UI/API 의존성 제거**. 9번 전체 초기화 도구, 10번 실제 원본 파일 전환/정합성 대사는 그 다음이다.
