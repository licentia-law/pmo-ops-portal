# Codex 작업 하네스

Codex가 PMO 업무수행 관리시스템을 수정할 때 매번 먼저 확인할 핵심 규칙이다.  
작업 성격별 상세 기준은 아래 문서를 필요한 경우에만 참고한다.

- 화면/프론트: [frontend_guide.md](frontend_guide.md)
- API/백엔드: [api_guide.md](api_guide.md)
- 검증·완료 보고: [verification_guide.md](verification_guide.md)

---

## 1. 작업 원칙

- 가정/추측하지 말고 기존 코드와 참조를 `rg`로 확인해 현황/맥락을 정확하게 파악 및 기획 후 작업 진행한다.
- MVP 범위에서는 가장 단순한 구조로 해결한다.
- 기존 패턴, 컴포넌트, helper를 먼저 찾고 재사용한다.
- 새 추상화는 실제 중복이나 책임 분리가 확인될 때만 추가한다.
- DTL에서 제외한 기능은 구현하지 않는다.
- 사용자 변경분은 되돌리지 않는다. 관련 없는 dirty file은 그대로 둔다.
- 새 운영 의존성이나 프로덕션 패키지를 추가하기 전에는 필요성, 기존 코드/패키지로 해결 가능한 대안, 운영 영향을 설명하고 사용자 확인을 받는다.
- 승인된 의존성 추가는 해당 선언 파일과 기존 lock 파일을 필요한 범위에서 함께 반영한다. 요청과 무관한 패키지 추가·버전 변경은 피한다.

## 2. 정책과 현재 구현의 구분

- 변경 목표는 사용자 확정사항과 적용 DTL을 따른다. 파일명 날짜만으로 최신 여부를 판단하지 않고 문서 내부 업데이트, 우선 적용 절, 적용 범위를 확인한다.
- DTL의 과거 구현 설명과 확정 정책을 구분한다. 명시된 우선 적용 절을 따르되, 해결되지 않은 문서 간 충돌은 근거와 함께 알리고 임의로 결정하지 않는다.
- 현재 구현 여부는 라우트·화면·API·모델 등 실제 코드에서 확인한다. 코드에 남아 있는 동작을 최신 정책으로 간주하거나 DTL 목표를 구현 완료로 표현하지 않는다.
- 정책과 코드가 다르면 현재 구현, 적용 목표, 남은 차이를 구분해 설명하고 요청 범위 안에서만 변경한다. 주요 차이와 근거는 [정책/구현 비교표](policy_implementation_status.md)를 참고하되 작업 시 다시 확인한다.

## 3. 분야별 구현 기준

- 화면은 얇은 라우트와 기존 공통 UI를 유지하고, 필터 적용·저장 후 재조회·메뉴 노출은 [프론트 가이드](frontend_guide.md)의 1~5절을 따른다. 별도 보고서 다운로드 페이지는 만들지 않는다.
- KPI/MM/가동률 등 업무 계산은 백엔드 기준으로 처리한다. 공통 파일, API 응답·코드값·계산 기준은 [API 가이드](api_guide.md)의 1~7절을 따른다.
- 권한 변경은 UI·직접 URL·API·데이터 범위를, DB 변경은 모델·스키마·마이그레이션·기존 데이터 정합성을 함께 확인한다. 상세 원칙은 [API 가이드](api_guide.md)의 10절, 삭제/정리 및 변경 검증은 [검증 가이드](verification_guide.md)를 따른다.

## 4. 검증·완료 보고

- 변경 영향에 필요한 최소 검증은 별도 요청 없이 수행한다. 브라우저 확인은 사용자가 담당하며 Codex는 브라우저를 열어 검증하지 않는다. 종류별 기준·명령과 문서만 변경한 경우의 생략 기준은 [검증 가이드](verification_guide.md)의 1절을 따른다.
- 변경 파일·핵심 내용·검증 결과·남은 확인 사항을 짧게 보고한다. 실패/미실행 사유와 사용자 브라우저 확인 항목은 [검증 가이드](verification_guide.md)의 8절을 따른다.
