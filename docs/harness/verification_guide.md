# 검증 가이드

스크립트 검증, 인력 숫자 검증, 권한 검증, seed DB 기준 검증을 정리한다.  
Codex는 검증 범위를 정하거나 완료 보고를 작성할 때 이 문서를 참고한다.

---

## 1. Codex 검증 범위

- Codex는 변경 영향에 따라 필요한 최소 검증을 선택해 수행한다. 필요한 검증은 별도 요청 없이 진행하며, 전체 검증을 매번 일괄 실행하지 않는다.
- 브라우저에서의 화면·동작 확인은 [핵심 가이드 4절](dev_guide.md)의 기준에 따라 Codex가 기본적으로 수행하고, 필요한 경우 사용자가 추가 검증한다. 데이터를 변경하는 브라우저 검증은 임시 DB/실제 DB 사본의 별도 환경을 사용한다. 도구·환경 제약으로 직접 확인하지 못한 항목은 사유와 추가 확인 방법을 남긴다.
- 문서만 변경한 경우에는 테스트·타입 검사·린트·빌드를 생략하고 변경 내용과 참조의 일관성을 확인한다.
- 검증 실패/미실행과 남은 확인 사항은 8절의 완료 보고 기준에 따라 남긴다.

변경 종류별 검증 기준:

| 변경 종류 | 필요한 최소 검증 |
|---|---|
| 문서만 변경 | 변경 내용, 참조 경로, 관련 문서와의 일관성 확인 |
| 프론트 코드·타입 변경 | 영향받는 workspace 타입 검사, 웹 코드 변경 시 관련 파일 린트 |
| 라우트·의존성·빌드 설정 변경 | 관련 타입 검사·린트 및 웹 빌드 |
| API·계산·권한 변경 | 변경 동작과 연결된 기존 백엔드 테스트, 프론트 연계 변경 시 해당 검증도 수행 |
| DB 스키마 변경 | 임시 DB에서 마이그레이션 테스트 및 관련 API·데이터 정합성 테스트 |

- 여러 종류에 해당하면 필요한 검증을 함께 수행한다. 프론트 변경도 타입 검사·린트만으로 확인하기 어려운 경우 빌드를 추가한다.
- 명령 예시: 저장소 루트에서 `npm.cmd run typecheck -w @pmo/web`, `npm.cmd run lint:web -- --file design/pages/ExecutionPage.tsx`, `npm.cmd run build:web`. workspace와 파일 경로는 변경 대상에 맞춘다.
- 공통 타입 등 여러 workspace에 영향이 있으면 루트의 `npm.cmd run typecheck`로 연관 범위를 확인한다.
- 백엔드는 `apps/api`에서 프로젝트 가상환경 Python으로 `python -m pytest tests/test_p1_api.py -k <관련_테스트명>`처럼 관련 테스트를 선택한다. 스키마 변경은 `python -m pytest tests/test_alembic_migrations.py`를 포함하며 개발용 DB에 직접 적용해 검증하지 않는다.
- 검증 도구·설정·의존성이 없어 실행할 수 없으면 그 이유와 대체 확인 방법을 남긴다. 실패 원인이 기존 문제인지 이번 변경 때문인지 구분한다.

## 2. 구현 전 체크

- [핵심 가이드](dev_guide.md)의 작업·정책 기준에 따라 적용 DTL의 확정 라우트/API와 현재 코드를 비교하고, 새 파일을 만들기 전 같은 책임의 기존 구현을 찾는다.
- 메뉴/라우트 변경은 [프론트 가이드](frontend_guide.md)의 2~3절을 따른다.

## 3. 구현 중 체크

- mock은 초기 레이아웃 확인에만 사용하며, 완료 기준은 실제 API 연결과 seed DB 기준 동작이다.
- 필수값 검증은 프론트와 백엔드 모두에서 수행한다.
- 권한/메뉴 노출 조건이 있는 화면은 7절에 따라 메뉴·직접 URL·API 권한을 점검한다.

## 4. 구현 후 공통 체크

- 1절의 기준에 따라 변경 영향에 필요한 검증을 수행한다.
- 목록 조회, 필터, 등록, 수정, 상세 이동, 다운로드 중 변경에 영향받는 동작을 코드·관련 테스트로 확인하고, 브라우저 확인 항목은 사용자에게 안내한다.
- 문서에서 정한 제외 범위가 구현에 섞이지 않았는지 확인한다.
- 신규 공통 기능이 생겼다면 중복 화면이 같은 모듈을 쓰도록 정리한다.
- seed DB 기준으로 KPI 카드, 목록 행 수, 상태별 요약 숫자가 서로 일치하는지 확인한다.

### DB 변경 시 추가 확인

- 임시 DB에서 새 DB 구성뿐 아니라 기존 스키마·대표 데이터의 전환 결과도 확인한다. 기존 migration 테스트가 변경된 데이터 전환까지 검증하는지 확인하고 부족한 범위만 보완한다.
- 전환 후 필수값·유일성·UUID/FK 참조, 기준값 중복, 관련 API 응답과 변경에 영향받는 MM·스냅샷·KPI의 정합성을 확인한다.
- 변경된 데이터 반영 경로의 실패 시 롤백/복구 범위를 확인하고, 자동 복구할 수 없는 부분은 완료 보고에 남긴다. 실제 개발/운영 DB를 검증용으로 초기화하지 않는다.

## 5. 삭제/정리 체크

- 라우트/메뉴 삭제 시 `routes.ts`, `menu.ts`, page·legacy 파일, 관련 컴포넌트·mock·디자인 소스·참조 문자열을 `rg`로 함께 확인한다.
- enum 삭제 시 백엔드 enum과 프론트 shared types를 함께 확인한다.
- 메뉴 정리는 [프론트 가이드](frontend_guide.md)의 제외 정책을 확인하고, 보고서/다운로드 별도 페이지가 되살아나지 않았는지 점검한다.

## 6. 인력 투입 현황 숫자 검증

- KPI 카드 합계와 현재 인원 스냅샷 행 수가 맞는지 확인한다.
- 수행/제안/지원/대기 수가 상태별 요약과 일치하는지 확인한다.
- 특정 인력 상세의 현재 배정과 현재 스냅샷의 대표 상태/프로젝트가 일치하는지 확인한다.
- 차기 투입 예정 목록과 배정 시작일 기준 결과가 일치하는지 확인한다.

## 7. 권한 검증

- 적용 DTL의 조회·등록·수정·엑셀 등 허용 범위와 [API 가이드](api_guide.md)의 10절을 기준으로 허용/비허용 사용자의 API 결과·데이터 범위를 검증한다. 비허용 요청은 실행을 차단하고 기존 데이터를 변경하지 않아야 한다.
- read only 등 기본 권한과 조직역할·기능 권한을 함께 확인한다. 인력 관리의 본부장 예외와 미확정 충돌은 [정책/구현 비교표](policy_implementation_status.md)에 따라 재확인하며, 허용/차단을 임의로 결정하지 않는다.
- 메뉴/버튼 노출과 직접 URL 접근은 별도로 확인한다. Codex가 기본 브라우저 검증을 수행하고 필요한 사용자 추가 확인 항목을 안내한다. 백엔드는 프론트 노출 여부와 관계없이 권한을 검증한다.

## 8. 완료 보고

- 변경 파일과 핵심 변경 내용을 짧게 요약한다.
- 실행한 검증 명령과 결과를 적는다.
- 검증 실패 원인, 필요한 검증의 미실행 사유와 남은 확인 사항을 적는다.
- 화면 동작에 영향이 있으면 사용자가 브라우저에서 확인할 동작과 기대 결과를 짧게 적는다.
